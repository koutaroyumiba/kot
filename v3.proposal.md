# Version 3 Website Proposal

## Status and source of truth

This document is the single source of truth for the version 3 redesign of `koutaroyumiba.com`. It contains the product direction, design specification, architecture decisions, implementation sequence, versioning policy, release process, and definition of done.

If implementation details conflict with this proposal, update this document deliberately before changing the implementation. Do not maintain separate migration, design, or implementation-plan documents.

## Purpose

Evolve the existing website into a precise, minimal CLI-inspired personal site without turning it into a simulation of Neovim or a desktop interface.

The redesign will:

- Continue using Astro.
- Continue deploying a static site to GitHub Pages.
- Preserve existing public URLs.
- Replace the current page-by-page styling with a consistent design system.
- Add the new `home`, `work`, `writing`, and `reading` information architecture.
- Keep LeetCode, projects, books, friends, the checklist, and the changelog available.
- Use small client-side scripts only where interaction is required.
- Avoid adding a backend.
- Avoid adding Svelte or another client framework unless a feature cannot be implemented cleanly with Astro and a small script.

Version `3.0.0` should represent the complete redesign. Incomplete redesign work should remain on a branch or use prerelease versions rather than being published as `3.1.0`, `3.2.0`, and so on.

## Core principle

> A clean personal site created by a Neovim user—not a website pretending to be Neovim.

The foundation should remain close to the current site: one centred content column, monospace typography, CLI commands as headings, mostly text-based content, minimal decoration, and fast static output. The “wow factor” should come from precision, polished code presentation, and a few memorable interactions rather than additional interface chrome.

## Architecture decisions

| Area | Decision |
| --- | --- |
| Repository | Continue using the existing `kot` repository |
| Production domain | Continue using `koutaroyumiba.com` |
| Framework | Continue using Astro |
| Rendering | Static generation by default |
| Hosting | Continue using GitHub Pages for version 3 |
| Backend | None required |
| Interactive UI | Small progressively enhanced scripts where possible |
| Client frameworks | Do not add Svelte solely for the redesign; remove React if it becomes unused |
| Existing routes | Preserve them wherever possible |
| Previous version | Preserve through Git history/tags rather than a permanent v1 subdomain |

A separate v1/v2 website would duplicate content, navigation, deployments, and maintenance. A frequently updated personal website does not inherently require server rendering: Git-based content can trigger a static rebuild. If future functionality requires authentication, database writes, comments, private administration, or live server-side data, reassess hosting and use an Astro server adapter at that time. Vercel is the default future option; Cloudflare Workers is appropriate if D1, R2, KV, or other Cloudflare services become concrete requirements.

## Approved design specification

### Visual direction

Use a minimal terminal-influenced design with:

- A charcoal dark background rather than pure black.
- A warm off-white light background rather than pure white.
- Soft cream primary text and muted grey-green secondary text.
- Green for paths and active states.
- Rose for commands.
- Gold for arguments and highlights.
- Blue and violet only as restrained secondary-category colours.
- Iosevka throughout the interface.
- One centred content column approximately `900px` wide.
- Narrower readable widths for long-form prose.
- Thin borders separating sections and rows.
- Generous but controlled vertical spacing.
- Minimal contained surfaces except where a code block or dialog requires one.

Hierarchy must come primarily from colour, weight, spacing, borders, and compact size changes. Avoid oversized editorial headings.

### Command headings

Use CLI commands as visible page and section headings:

```text
~/about/me $ cat desc
~/work $ ls --sort=impact
~/writing $ grep -R "unfinished ideas"
~/reading $ sqlite3 library.db "select * from books"
```

Command headings must wrap safely on narrow screens and remain understandable to assistive technology. Colour should reinforce their parts, not serve as the only distinction.

### Structured lists

Projects, writing, books, and LeetCode should use compact rows rather than large cards or complicated grids. Rows may contain an index/date/status, title, short description, category/technology metadata, and a restrained arrow. Use subtle hover/focus backgrounds and a small horizontal shift, disabled under reduced-motion preferences.

### Code presentation

Code blocks should be among the strongest visual moments. Provide syntax highlighting, optional line numbers where useful, optional filename/language metadata, a restrained terminal-style frame, strong contrast in both themes, and horizontal scrolling on narrow screens. Do not imitate a complete editor window.

### Motion

Allow only restrained motion such as a blinking cursor in the wordmark or active prompt, small row shifts, colour transitions, and command-palette feedback. Respect `prefers-reduced-motion`. Do not add typing introductions, fake loading screens, or animations that delay access to content.

### Navigation

Primary navigation is:

```text
home   work   writing   reading
```

The header contains the `~ / ky` wordmark, primary links, visible `:jump` button, and theme toggle. LeetCode, contact, changelog, and other destinations remain discoverable through page links, `/contents`, and `:jump`. Conventional navigation must work without JavaScript.

### `:jump` interaction

The optional command palette must:

- Open through its visible button.
- Open with `:` outside editable controls.
- Open with Cmd/Ctrl+K.
- Filter destinations as the user types.
- Support arrow-key selection and Enter.
- Close with Escape and restore focus.
- Optionally display Vim-style hints such as `g w`.
- Supplement rather than replace conventional navigation.

### Responsive behavior

- Preserve the single-column layout.
- Let navigation wrap cleanly.
- Hide nonessential row metadata before essential content.
- Wrap command headings without page-level horizontal overflow.
- Make code blocks independently scrollable.
- Keep the ASCII signoff legible by scaling it down when necessary.
- Maintain comfortable touch targets.

### Accessibility requirements

- Use semantic headings, lists, controls, and landmarks.
- Maintain strong contrast in both themes.
- Provide visible keyboard focus.
- Make `:jump`, theme controls, and filters keyboard accessible.
- Never rely on colour alone for status.
- Respect reduced-motion preferences.
- Keep the site navigable without JavaScript.

### Explicitly excluded

Do not add:

- Full desktop or editor simulations.
- Tabs or buffer interfaces.
- File trees or explorer/context sidebars.
- Persistent Neovim status bars.
- Oversized editorial headings.
- Large project-card grids.
- Excessive visual effects.
- Generic portfolio layouts.
- Terminal conventions that make navigation harder.

### Page requirements

**Homepage:** concise about section; current reading/building/coffee/music status; ASCII `KOT` ending; and the line `build things. read widely. stay curious.`

**Work:** structured project list and substantive detail pages covering motivation, constraints, decisions, trade-offs, outcomes, lessons, screenshots, and relevant code where available.

**Writing:** list of essays with abstract, topic, reading time, and date; position writing as thinking in progress rather than declarations of certainty.

**Reading:** catalogue rows with status, title, author, rating, completion date, optional note, and client-side filters for all, reading, read, unread, and favourites.

**LeetCode:** list rows with date, question number/title, difficulty, topics, and solution link; solution pages use the shared long-form and code-block treatment.

**Personality:** retain references to Neovim, coffee, reading and philosophy, ONE OK ROCK, Smiskis, teaching, and community work naturally in writing and status content rather than as large decorative features.

## Versioning and Git strategy

### Correct the preservation strategy

Do not tag the current site as `v1.0.0`: the changelog already records versions `1.0.0`, `1.1.0`, and `2.0.0`.

Use the following version history instead:

- `v1.0.0`: original launch, if a historical tag is ever reconstructed.
- `v1.1.0`: books-page release, if a historical tag is ever reconstructed.
- `v2.0.0`: Rose Pine theme redesign represented by the existing changelog.
- `pre-v3-redesign`: optional snapshot of the last commit before version 3 implementation begins.
- `v3.0.0`: completed redesign described by this plan.

The Git history indicates that commit `b2b001a` added the `2.0.0` changelog entry. If historical tags matter, inspect the surrounding commits and tag the commit that represents the complete 2.0 release—not merely the current `HEAD` by default.

### Prepare the branch

Before branching:

1. Run `git status`.
2. Review the local commit that has not yet been pushed.
3. Review this proposal and resolve any undecided scope before implementation.
4. Commit or intentionally discard any outstanding files.
5. Push the intended baseline to `origin/main`.
6. Create the redesign branch.
7. Optionally create the `pre-v3-redesign` snapshot tag.

Suggested branch:

```bash
git switch -c redesign/v3
```

Suggested milestone tags, only if preview releases are useful:

```text
v3.0.0-alpha.1   shared shell and design system
v3.0.0-alpha.2   content and data migration
v3.0.0-beta.1    all primary pages implemented
v3.0.0-rc.1      feature-complete accessibility/testing candidate
v3.0.0           production release
```

Do not add every prerelease to the public changelog unless visitors can actually access those versions. The public changelog should normally receive one consolidated `3.0.0` entry at launch.

Define variables for both dark and light themes. Keep the current Rose Pine influence, but formalize semantic names rather than using page-specific colours.

Suggested token categories:

```css
:root {
  color-scheme: dark;

  --color-bg: ...;
  --color-surface: ...;
  --color-surface-hover: ...;
  --color-text: ...;
  --color-text-muted: ...;
  --color-border: ...;
  --color-path: ...;
  --color-command: ...;
  --color-argument: ...;
  --color-link: ...;
  --color-focus: ...;
  --color-success: ...;
  --color-warning: ...;
  --color-danger: ...;

  --font-mono: "Iosevka", ...;
  --content-width: 56.25rem; /* 900px */
  --reading-width: 44rem;
  --header-height: ...;

  --space-1: ...;
  --space-2: ...;
  --space-3: ...;
  --space-4: ...;
  --space-6: ...;
  --space-8: ...;
  --space-12: ...;

  --border-width: 1px;
  --radius-small: ...;
  --transition-fast: ...;
}
```

Use either a class or a `data-theme` attribute consistently. A `data-theme="light"`/`data-theme="dark"` approach is clearer than the current `theme-light` class.

### Global rules

Implement:

- `box-sizing: border-box` globally.
- Stable body margin, minimum height, background, and text colour.
- A centred `.site-shell` constrained to approximately `900px`.
- Comfortable body line height.
- Consistent heading, paragraph, list, and link spacing.
- Visible `:focus-visible` outlines.
- Styled text selection.
- Responsive media defaults (`img`, `svg`, `video`).
- Horizontal overflow protection.
- Screen-reader-only utility class.
- Skip-link styling.
- Reduced-motion overrides.
- Print-friendly defaults if straightforward.

Do not use global `span` colour rules. Colour should come from meaningful classes such as `.command-heading__path`, `.command-heading__command`, and `.command-heading__argument`.

### Font loading

Bundle Iosevka locally through `@fontsource/iosevka` rather than loading a font from Google Fonts:

- Include sensible monospace fallbacks.
- Import only the required `400`, `500`, and `600` weights.
- Keep `font-display: swap` behavior so text remains visible during loading.
- Avoid external font requests and unnecessary render blocking.

Known issue: each bundled Iosevka weight is currently approximately `960 KB`. On an uncached load, the fallback monospace font renders larger before Iosevka replaces it, causing a visible text-size shift. Do not preload the current files blindly because that would move a large font download onto the critical path. During release polish, measure the production behavior and prefer reducing the payload through an Iosevka subset, fewer weights, or an appropriate variable-font build before considering preload. The temporary development-mode shift is accepted for Phase 1.

- [ ] The body does not horizontally overflow at 320px.
- [ ] Text remains readable if the web font fails.
- [ ] Reduced-motion mode removes nonessential transitions.
- [ ] Existing pages remain usable while the new styles are introduced.

- Semantic heading level.
- Path text.
- Prompt text.
- Command text.
- Optional arguments.
- Optional hostname/user prefix for commands such as `kot@auckland ~/now`.
- Wrapping on narrow screens.

- One-column or simplified grid at narrow widths.

# Changelog plan

## Public versioning policy

Use semantic versioning for meaningful website releases:

- **Major (`3.0.0`)**: site-wide design/information-architecture change or a deliberately incompatible content structure.
- **Minor (`3.1.0`)**: a substantial backward-compatible feature such as RSS, search, or a new content section.
- **Patch (`3.0.1`)**: accessibility, styling, metadata, typo, or broken-link fixes that do not introduce a substantial new feature.
- **Prerelease (`3.0.0-beta.1`)**: optional preview milestone, normally omitted from the public changelog.

Daily LeetCode entries and ordinary content updates do not need a new application version unless the changelog is intended to record all content publishing.

## Proposed internal version states

| Version | State | Exit criteria |
| --- | --- | --- |
| `3.0.0-alpha.1` | Foundation | Tokens, global styles, layout, header, footer, and theme work |
| `3.0.0-alpha.2` | Data migration | Content schemas, books extraction, and LeetCode migration work |
| `3.0.0-beta.1` | Feature complete | Home, work, writing, reading, LeetCode, palette, and secondary pages implemented |

# Recommended commit sequence

The following sequence keeps reviews focused and makes regressions easier to locate:

```text
chore(v3): preserve redesign baseline and content inventory
feat(v3): establish design tokens and global styles
feat(v3): rebuild shared layout and metadata
feat(v3): replace header and theme controls
feat(v3): add shared footer
feat(v3): add command, list, and prose primitives
refactor(v3): define content collection schemas
refactor(v3): extract books and site data
refactor(v3): migrate leetcode entries without changing URLs
feat(v3): implement redesigned homepage
feat(v3): rebuild work index and project case studies
feat(v3): add writing collection and preserve thoughts route
feat(v3): rebuild reading catalogue and filters
refactor(v3): remove unused React integration
feat(v3): add accessible jump command palette
feat(v3): redesign secondary pages and error state
feat(v3): add page metadata and release polish
docs(v3): add version 3 changelog entry
fix(v3): address release candidate review findings
```

This is a guide, not a requirement to create empty or artificial commits. Keep each actual commit buildable whenever practical.

# Definition of done for `3.0.0`

Version 3 is complete when all of the following are true:

## Product

- [ ] The approved minimal CLI direction is recognizable on every page.
- [ ] The site feels like a personal site made by a Neovim user, not a Neovim simulation.
- [ ] Home, work, writing, and reading are the primary navigation destinations.
- [ ] LeetCode and secondary pages remain discoverable.
- [ ] Personal voice and humour are retained.

## Content

- [ ] Existing content has been audited rather than copied blindly.
- [ ] No published project links lead to missing pages.
- [ ] Book metadata is consistent.
- [ ] LeetCode URLs and entry counts are preserved.
- [ ] Draft writing and projects are not accidentally published.

## Design

- [ ] Layout is constrained to roughly 900px.
- [ ] Typography uses Iosevka with reliable fallbacks.
- [ ] Dark and warm-light themes are complete.
- [ ] Command headings use path, command, and argument colours consistently.
- [ ] Lists replace unnecessary cards and grids.
- [ ] Code blocks are polished and horizontally scrollable.
- [ ] Motion is subtle and optional.

## Accessibility

- [ ] Conventional navigation works without JavaScript.
- [ ] Theme, filters, and palette are keyboard accessible.
- [ ] Focus is visible everywhere.
- [ ] Reduced motion is respected.
- [ ] Colour is not the only status indicator.
- [ ] Mobile and zoomed layouts do not hide content.

## Technical

- [ ] Astro remains statically generated.
- [ ] GitHub Pages deployment still works.
- [ ] Shared content has typed schemas or interfaces.
- [ ] No unnecessary client framework is added.
- [ ] React is removed if no React island remains.
- [ ] No debug output or dead starter code remains.
- [ ] `npm run build` succeeds from a clean checkout.

## Release

- [ ] Changelog includes an accurate `3.0.0` entry.
- [ ] The release commit is tagged `v3.0.0`.
- [ ] Production smoke tests pass.
- [ ] Follow-up issues are recorded without modifying the release tag.
